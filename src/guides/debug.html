Chapter 6

Debug and ship

Most MCP bugs are one of six things. Here they are, in the order you'll hit them.

The classic failures

Symptom Cause Fix
Client reports parse errors, or the connection dies instantly You wrote to stdout — a console.log, a banner, a dependency's startup message stdout is the protocol channel. Log to stderr only.
Works with small payloads, breaks with large ones Treating each stdin chunk as one message Buffer and split on newlines (Chapter 4, step 1).
Every request rejected with -32602 Client isn't sending _meta, or the server forgot to expect it Both protocolVersion and clientCapabilities are required on every request.
Client errors on your results Missing resultType, or missing ttlMs/cacheScope on a list result Stamp resultType: "complete" centrally; add the cache fields to every list result.
Second tool call doesn't remember the first Assuming a session — the protocol has none Return an explicit handle and take it as a tool argument.
The model gives up after one failed call Tool failures returned as JSON-RPC errors Return isError: true with a message the model can act on.
Era mismatch looks like a broken server. A legacy client sending initialize to a modern server, or a modern client sending _meta to a legacy one, fails in confusing ways — silence, an unknown-method error, or worse, a legacy server happily processing the request under legacy semantics. Check which revision each side speaks before debugging anything else.

Logging

Use console.error(). The protocol's own logging feature is deprecated as of 2026-07-28; stderr (or OpenTelemetry, with trace context propagated in _meta) is the recommended path. Clients must not treat stderr output as an error signal.

The Inspector

The official interactive debugger. Lists your tools, lets you call them with arbitrary arguments, and shows the raw traffic. 

npx @modelcontextprotocol/inspector       # then point it at http://127.0.0.1:3001/mcp

Use it before wiring the server into a real client — it isolates your bugs from the host's.

Description quality is the whole game

The model chooses tools from names, descriptions and schemas alone. It cannot read your source.

Weak

"description": "Gets data" — the model can't tell when to use it, what it returns, or what the arguments mean.

Strong

"Search open GitHub issues in a repo by keyword. Returns at most 20 matches, newest first. Use for questions about bug reports; use get_issue for a known number."

Say what it does, when to use it, when not to, and what comes back. Describe every parameter, constrain with enum and default, and document handle lifetimes ("baskets expire after 24 hours") in the creating tool's description.

Security checklist

  • Validate every input. Arguments come from a model reacting to text that may be attacker-controlled. Treat them as untrusted user input.
  • Treat requestState as hostile. It round-trips through the client. Integrity-protect it, bind it to the principal, expire it, and reject what fails verification.
  • Handles are names, not capabilities. Re-authorize on every call — a stateless protocol means the previous call proves nothing.
  • Confine paths. Resolve and check against an allowed root; reject .. traversal explicitly.
  • Never return secrets in tool output — it goes straight into the model's context. Don't mark sensitive parameters with x-mcp-header either; header values are visible to intermediaries.
  • Keep tools narrow. A run_shell_command tool hands the model your whole machine.
  • Don't dereference network $refs in JSON Schema by default, and bound schema depth — a malicious schema is a DoS vector.
  • For HTTP transports: validate the Origin header (DNS rebinding), bind local servers to 127.0.0.1, require auth. A token issued for another service must never be accepted or forwarded.
  • Rate-limit and time-box anything hitting an external API; a model in a retry loop is a load generator.

Shipping

  1. Advertise every revision you support in server/discover, and decide deliberately whether to be modern-only or dual-era.
  2. Return tools in a deterministic order, with honest ttlMs — it's what keeps clients from polling you.
  3. Take config from environment variables, never hardcoded credentials.
  4. Exit promptly when stdin closes; that's the only portable shutdown signal. Expect clients to restart you and retry — in-flight requests are simply lost, and that's fine now.
  5. Deploy it behind TLS with real token validation; document the exact connection details — URL, required scopes, and which protocol revision you speak.
  6. Version your tool names. Renaming a tool breaks every prompt that mentions it.
