Chapter 3

The primitives

Three things a server offers. The useful mental model is who is in control — and, since 2026-07-28, how a server asks for something back without holding a session open.

"Controlled by" means who decides to invoke it — not who sends the request. Every one of these arrives as a call from the client; only for tools is the client acting on the model's choice. Who calls what →

Tools — model-controlled

The model picks them from name, description and schema alone, so the description is prompt engineering, not documentation. 

{
  "name": "search_issues",
  "title": "Search issues",
  "description": "Search GitHub issues in a repo. Returns at most 20 matches, newest first.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "repo":  { "type": "string", "description": "owner/name, e.g. facebook/react" },
      "query": { "type": "string" },
      "state": { "type": "string", "enum": ["open", "closed", "all"], "default": "open" }
    },
    "required": ["repo", "query"],
    "additionalProperties": false
  }
}

Names should stick to A-Za-z0-9_-. and stay under 128 characters. A tool with no parameters still needs a schema: { "type": "object", "additionalProperties": false }. An optional outputSchema constrains structuredContent, which may be any JSON value.

Annotations (hints, not enforcement)

Hosts use these to decide what needs confirmation. Clients must treat them as untrusted unless the server is trusted.

Hint Means
readOnlyHint Changes nothing. Hosts may run it without asking.
destructiveHint May delete or overwrite. Expect a confirmation dialog.
idempotentHint Calling twice with the same args is the same as once.
openWorldHint Touches the outside world (network, external API).
All three are implemented in this repo. server.tool(), server.resource() and server.prompt() in src/mcp/server.ts; the dispatch for each is in src/mcp/sdk/server.ts. A server only advertises the capabilities it actually has something registered for.

Resources — app-controlled

Read-only data your server exposes, addressed by a URI. Think "files the server can hand over." No side effects, and resources/read twice should give the same thing.

The defining trait: the model does not decide to fetch them. The application or the person does. That is the entire difference from a tool. 

// static — an exact uri
{ "uri": "file:///logs/app.log", "name": "app-log", "mimeType": "text/plain" }

// templated — RFC 6570, {variable} expansion
{ "uriTemplate": "db://users/{userId}", "name": "user-record" }

When they are called

client connects
  -> resources/list            the exact-uri ones (dice://notation)
  -> resources/templates/list  the patterns (dice://odds/{sides})
     ... client caches both, honouring your ttlMs ...

someone attaches or references one
  -> resources/read { uri: "dice://odds/20" }
  <- contents [...]            the text becomes conversation context

Two requests at connection time to populate a picker, then a read when someone picks. Your reader runs only at that last step, and receives whatever the template captured: 

server.resource(
  { name: "dice-odds", uriTemplate: "dice://odds/{sides}", mimeType: "text/plain" },
  ({ uri, variables }) => ({
    contents: [textResource(uri, `A d${variables.sides} rolls each face ...`)],
  }),
)

Exact uris are matched first, then templates. A uri matching neither is -32602 — the code that replaced the retired -32002 in this revision.

Where they show up

In a host that supports resources: /mcp lists the server and confirms resources/list succeeded, and resources are referenced with @ mentions namespaced by server. Type @ and read the autocomplete — that is authoritative for your client version, and the surface differs between hosts.

Your template will not appear in a picker. resources/list returns only exact uris, so a menu can offer dice://notation but not dice://odds/{sides} — there is nothing to enumerate, {sides} is infinite. Templates come from resources/templates/list, and whether a client offers a fill-in-the-blank UI is up to it. If you want something discoverable in a menu, register concrete uris.

So why not just make it a tool?

Honestly, for most read-only data a tool would work too, and the model could fetch it unprompted. Reasons to choose a resource:

  • It costs no model tokens to decide. Nothing enters the prompt until a person attaches it.
  • It is the right shape for reference material a user browses, rather than an action.
  • There is nothing to abuse. Read-only, no arguments beyond the uri, nothing to validate.

Against that: resources are the least-supported primitive. Plenty of clients implement tools only, and a server that hides something important behind a resource may find nobody ever reads it.

The test for resource versus tool. If the model should be able to fetch it mid-turn, it is a tool. If a person picks it, it is a resource. When in doubt ship the tool — it works everywhere.

Prompts — user-controlled

A prompt is a saved message with holes in it. A person picks it off a menu, the client fills the holes with their arguments, and the result is dropped into the conversation as if they had typed it.

The messages you return are input, not output. Your server is not answering the user — it is writing the user's message for them. Nothing you return here is shown as a reply. 
server.prompt(
  {
    name: "explain-roll",
    arguments: [{ name: "notation", required: true }, { name: "context" }],
  },
  (args) => ({ messages: [userMessage(`Roll ${args.notation} and explain the odds`)] }),
)

What comes back over the wire:

{
  "description": "Roll 3d20 and explain the odds",
  "messages": [
    { "role": "user", "content": { "type": "text",
      "text": "Roll 3d20 using the roll_dice tool for a boss fight, then explain how likely that total was." } }
  ]
}

What happens next

The client seeds the conversation with those messages and runs an ordinary model turn. Because this particular text tells the model to use a tool, one slash command sets off both a prompts/get and a tools/call — and the user sees only the final prose. 

user picks /explain-roll, fills in notation=3d20
  -> prompts/get { name, arguments }     client asks your server
  <- messages [...]                      your server returns the text
     client seeds the conversation with those messages
     model turn begins — it reads "Roll 3d20 using the roll_dice tool..."
     model emits: use roll_dice { count: 3, sides: 20 }
  -> tools/call                          client sends it
  <- "Rolled 3d20: 11, 6, 2 (total 19)"
     model composes: "You rolled 19 — below average for 3d20, whose mean is 31.5..."
user sees THAT

Isn't that just a skill, or a slash command?

Essentially yes, and it is the most useful way to think about it: saved instructions injected into context, not code that computes an answer. The differences are worth knowing:

A local skill / slash command An MCP prompt
Lives In a file on disk On the server, fetched over the wire
Text Static, with placeholders substituted Generated per call — your handler runs and can query anything
Arguments Usually free-form Declared and validated; a missing required one is rejected with -32602
Triggered by A person, or sometimes the model A person, always
Can bundle Scripts, files, other resources Messages only

The dynamic part is the real difference: a prompt handler is code. It can read today's schema, the current sprint, the user's open tickets, and build the message from that — something a static file cannot do.

Three rules

  • description is for humans, messages are for the model. The client shows the description in its menu; only the messages reach the model.
  • Your server never learns what happened. prompts/get is one request, answered, done. You do not find out whether the model complied, called your tool, or ignored the instruction entirely.
  • You can prefill both roles. Alternating user and assistant messages seed a few-shot exchange, and the model treats the assistant turns as things it already said — which is why the SDK exports assistantMessage alongside userMessage.
The test for prompt versus tool. If you are tempted to compute the answer inside prompts/get, you want a tool. A prompt writes the request; a tool performs the work.

Asking the client for something: MRTR

Server-initiated requests are gone. A server that needs input mid-call answers with resultType: "input_required", and the client retries the whole request with the answers attached. Two independent requests, no session in between. 

// <- server needs input
{
  "resultType": "input_required",
  "inputRequests": {
    "github_login": {
      "method": "elicitation/create",
      "params": {
        "mode": "form",
        "message": "Please provide your GitHub username",
        "requestedSchema": { "type": "object", "properties": { "name": { "type": "string" } }, "required": ["name"] }
      }
    }
  },
  "requestState": "AEAD-protected blob"
}

// -> client retries the ORIGINAL request with a NEW id
{
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "New York" },
    "inputResponses": { "github_login": { "action": "accept", "content": { "name": "octocat" } } },
    "requestState": "AEAD-protected blob"
  }
}

Only tools/call, resources/read and prompts/get may return input_required. The values inside inputRequests are exactly the three former server-to-client requests: elicitation/create, sampling/createMessage, roots/list. A server must not request one the client didn't declare in clientCapabilities.

requestState is attacker-controlled. It travels through the client, so if it influences authorization or business logic you must integrity-protect it (HMAC or AEAD) and reject what fails verification. Bind it to the authenticated principal, give it a short TTL, and tie it to the originating request. Clients must echo it back byte-for-byte and never parse it.

Change notifications: subscriptions/listen

The HTTP GET stream and resources/subscribe are replaced by one long-lived request. The client opts into what it wants; the server tags each notification with io.modelcontextprotocol/subscriptionId. 

// -> subscriptions/listen { toolsListChanged: true, resourcesListChanged: true }
// <- notifications/subscriptions/acknowledged, then a stream of change notifications

Request-scoped notifications like notifications/progress still flow on the response stream of the request they belong to, not on this one.

Deprecated as of 2026-07-28

Still functional, but new servers should not adopt them:

Feature Do this instead
Roots Pass directories via tool parameters, resource URIs, or server config
Sampling Integrate an LLM provider API directly
Logging (notifications/message) Log to stderr on stdio, or use OpenTelemetry
HTTP+SSE transport Streamable HTTP

Removed outright: ping, logging/setLevel (log level is per-request via io.modelcontextprotocol/logLevel), and notifications/roots/list_changed. Tasks moved out of core into the io.modelcontextprotocol/tasks extension.

Choosing. If the model should decide when to run it, it's a tool. If it's data the app attaches, it's a resource. If a human picks it off a menu, it's a prompt. Most servers ship tools only — that's fine, and increasingly it's the whole recommended surface.
