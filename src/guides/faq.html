FAQ

Questions that come up

The things that trip people up, answered once. Each links to where the detail lives.

Who actually calls these methods — the model?

No. The client does. The model never emits JSON-RPC; it cannot call anything. It produces text and tool-use blocks, and the client translates one of those into a tools/call request.

Of the methods MCP defines, exactly one is model-driven: tools/call. Everything else — every list, server/discover, resources/read, prompts/get — is initiated by the client or by a human. Full table and ordering →

Concretely: what is the "client" when I open Claude Code?

Claude Code is the host. The client is not a separate program — it is an object inside Claude Code, one per configured server. Three servers in your config means three clients. Your server process is the server.

What happens when you open Claude Code, in order:

  1. Claude Code reads your MCP config and spawns your server as a subprocess, pipes attached.
  2. That connection's client sends server/discover, then tools/list and prompts/list. No model has run yet — you may not have typed anything. /mcp shows you the result.
  3. The returned tool definitions are injected into the model's context as available tools.
  4. You type "roll 3d20". The model emits a tool-use block; Claude Code converts it to tools/call and writes it to the pipe.
  5. Your server answers, and Claude Code feeds the result text back into the model's context.
Watch it happen. Add console.error("got:", line) in src/mcp/sdk/stdio.ts and start Claude Code: you will see server/discover and tools/list arrive before you type a single prompt.

Are the method names a convention I can extend?

No — tools/list, tools/call, resources/read, prompts/get, server/discover are fixed strings in the spec's schema, like HTTP verbs. Invent tools/fetch and every client answers -32601.

The extension point is namespaced: official extensions add methods under io.modelcontextprotocol/, third parties under their own reverse-DNS prefix. Never a bare new method name.

When does instructions reach the model?

It rides in the server/discover result and nowhere else. The client fetches it and decides what to do — typically prepending it to the system prompt once, at setup.

The catch: server/discover is optional for clients. A client may call tools/call inline and never discover at all, in which case your instructions is never read by anyone. Treat it as a droppable hint; anything a tool genuinely needs belongs in that tool's own description.

Isn't there supposed to be an initialize handshake?

Not since revision 2026-07-28. It was removed along with protocol-level sessions. Every request now carries its own protocol version and capabilities in _meta. Revisions up to 2025-11-25 are called legacy; anything you read describing a handshake is written for those. Chapter 2 →

Doesn't statelessness mean writing more code?

Slightly less, and simpler code. Writing the same server both ways in this repo: 213 lines modern, 291 legacy — the legacy version additionally needs a four-state phase machine, a guard on every dispatch, an outbound request-id space with a correlation table, keepalive probing, and session teardown. About 94 lines exist only to maintain a connection, against 19 spent validating _meta on every request.

On HTTP the gap is much wider: sessions meant a session store, sticky routing, a per-session SSE channel and an event-id replay buffer. All deleted. Chapter 5 →

How does the server discover its own resources and prompts?

It doesn't — there's no discovery magic anywhere in MCP. A server knows only what you registered on it, exactly like tools: 

server.tool(definition, (args, context) => ...)             // model-controlled
server.resource(definition, ({ uri, variables }) => ...)    // app-controlled
server.prompt(definition, (args) => ...)                    // user-controlled

The client then calls tools/list, resources/list or prompts/list and gets back what's registered. Chapter 3 →

What is the context argument my handler receives?

RequestContext — everything the server knows about this one call, and nothing else. In a stateless protocol there is no session object, so this replaces it: built fresh per request, thrown away after.

Member What it gives you
clientCapabilities / clientInfo Who is calling and what they support, from this request's _meta
progress(...) Report partial work. Real on a streaming transport when the client sent a progressToken; a no-op otherwise, so handlers never branch on transport
answer(key) The user's reply to an earlier elicit(), or undefined on the first call (and when they declined or cancelled)
elicit(key, ask) Ask a question and end the request; the client retries the whole call with the answer
requestState The opaque blob the client echoes back on that retry

answer and elicit are the two halves of one round trip, which is why they live together: 

const answer = context.answer<{ sides?: number }>("how_many_sides")
if (answer) return rollDice(1, Number(answer.sides ?? 6))   // second call
return context.elicit("how_many_sides", { message, schema }) // first call

Two separate requests, possibly served by different instances, written as one function.

When do resources get called, and where do they appear?

The client calls resources/list and resources/templates/list at connection time to populate a picker, then resources/read when a person attaches or references one. The model never decides to fetch a resource — that is the whole difference from a tool.

In Claude Code they surface as @ mentions namespaced by server; type @ and read the autocomplete for your client version. Note that a templated resource cannot appear in a picker — resources/list only returns exact uris — so register concrete uris for anything you want discoverable. Chapter 3 →

A prompt sounds like a skill or a slash command. Is it?

Essentially yes — saved instructions injected into context, not code that computes an answer. Two differences matter: an MCP prompt is generated per call by a handler that can query anything before writing the text, and its arguments are declared and validated rather than free-form. A local skill can also bundle scripts and files; a prompt returns messages only.

What happens after prompts/get returns?

The messages you return are input, not output. Your server is writing the user's message for them, not answering. The client injects them into the conversation as if the person had typed them, then runs a normal model turn — so if your text says "use the roll_dice tool", one slash command triggers a prompts/get and then a tools/call, and the user sees only the final prose.

Your server never learns the outcome: prompts/get is one request, answered, done. The full trace →

My tool failed. Error or result?

Result, with isError: true and the reason in content — the model reads it and self-corrects. Reserve JSON-RPC errors for unknown tools, malformed requests and server faults, which the model cannot fix. Getting this backwards is the most common beginner bug. Chapter 2 →

How do I keep state between two tool calls?

Return an explicit handle and take it back as an ordinary tool argument: 

// -> create_basket {}            <- { "basket_id": "bsk_a1b2c3" }
// -> add_item { "basket_id": "bsk_a1b2c3", "sku": "..." }

The model carries it forward. A handle is a name, not a capability: re-authorize on every call, keep it opaque, bound its lifetime, and say so in the creating tool's description.

Do I have to implement server/discover?

Yes — servers MUST. Clients MAY skip calling it. The asymmetry is deliberate: it is also the probe a dual-era client uses on stdio to tell a modern server from a legacy one.

Claude Code says "Failed to connect" to my server. Why?

Most likely an era mismatch. Run claude mcp get <name>: if the issue reads -32601: This server is stateless and has no initialize handshake, your client is legacy and your server is modern-only. Claude Code 2.1.263 opens with protocolVersion: "2025-11-25" — the handshake era.

There are two honest answers. Serve those clients by implementing the handshake era alongside the modern one — cheap on stdio, expensive over HTTP, where legacy also means Mcp-Session-Id, sticky routing and SSE resumability. Or stay modern-only and wait, which is what the SDK in this repo does. Check what your target clients speak before you build against the transport.

My HTTP endpoint rejects everything with -32020. Why?

A header disagrees with the body. Streamable HTTP mirrors method into Mcp-Method, params.name or params.uri into Mcp-Name, the _meta version into MCP-Protocol-Version, and any x-mcp-header argument into Mcp-Param-*. All are required, and the server must reject a mismatch rather than pick a side.

On the stdio transport the equivalent failure is writing to stdout — a console.log or a startup banner corrupts the protocol channel there. Chapter 6 →

Which revision am I actually speaking?

Check the date at the top of any spec page you read, and check what your SDK targets — the era matters more than the package version. A modern client against a legacy server (or the reverse) fails in confusing ways, including a legacy server happily processing a request under legacy semantics. Compatibility matrix →
