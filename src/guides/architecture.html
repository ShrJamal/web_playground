Chapter 1

Host, client, server

Three words for what looks like two boxes. The distinction still matters the moment you have more than one server connected — even though, since 2026-07-28, none of them holds a session.

One host, many clients, one server per client — a connection, not a session.

The three roles

Role What it is Who writes it
Host The application the user actually sits in. It owns the model, the conversation, and the permission decisions. Claude Code, Claude Desktop, Cursor, your own agent
Client A connector object inside the host. Talks to one server, and is where the transport, the auth, and the per-request _meta get attached. Almost always the host's SDK, not you
Server A separate program exposing capabilities. Knows nothing about the model or the conversation, and nothing about your previous request. You, most of the time
Why the client exists as its own concept. Isolation. A server can't see the other servers a host is connected to and can't reach into the conversation — that's a security boundary, not bookkeeping. What a client is not, as of 2026-07-28, is a session holder: an open stdio process is not a conversation, and a client may interleave unrelated requests on it.

Who calls what

The single most common confusion, worth settling before anything else: the model never emits JSON-RPC. It cannot call a method. It produces text and tool-use blocks; the client is what turns one of those into a request on the wire.

Only the middle column ever speaks MCP. The left column only ever proposes.

So of the methods MCP defines, exactly one is model-driven:

Method Who decides When
server/discover Client At connection setup — and it is optional
tools/list Client Setup, then when ttlMs expires or a list_changed notification arrives
resources/list Client Same, to populate an attachment picker
prompts/list Client Same, to populate a slash-command menu
tools/call Model (client sends it) When the model emits a tool-use block mid-turn
resources/read Client or user A person attaches a file, or app policy pulls one in
prompts/get User A person picks the slash command

Concretely, with Claude Code: Claude Code is the host, the client is an object inside it (one per configured server), and your server process is the server. Claude Code spawns that subprocess at startup and its client immediately discovers and lists — before you type anything. The full startup sequence →

The order in a real session:

client starts up
  -> server/discover     (client, optional)
  -> tools/list          (client — it needs the schemas to build the prompt)
  -> prompts/list        (client — populates the slash-command menu)
     ... tool definitions enter the model's context as available tools ...

user types something
     model emits: use roll_dice { count: 3, sides: 20 }
  -> tools/call          (client translates that into JSON-RPC)
  <- result
     ... the result text goes back into the model's context ...

user picks /explain-roll
  -> prompts/get         (client — no model involvement at all)
The consequence for you as a server author. By the time the model sees anything, listing has already happened — it chooses from a list and never asks for one. So tools/list output is prompt input, and your tool description is prompt engineering. Metadata the client consumes — instructions, resource titles, prompt descriptions — may never reach the model at all.

Transports

Two are defined. Both carry the same JSON-RPC messages; only the pipe differs.

stdio

The host spawns your server as a subprocess and speaks over stdin/stdout, one JSON message per line, no embedded newlines. Local, zero network, zero auth. All metadata rides inline in _meta — there is no header layer. Start here.

Streamable HTTP

One /mcp endpoint taking POSTs; responses come back as JSON or an SSE stream. No Mcp-Session-Id, no sticky routing, no stream resumability — any instance can serve any request. Requires MCP-Protocol-Version, Mcp-Method and Mcp-Name headers, plus auth and origin checks.

Rule of thumb. stdio for anything touching the user's own machine. Streamable HTTP when the server is a shared service other people connect to — and because it is stateless now, scaling it is ordinary horizontal scaling. (The old HTTP+SSE transport is deprecated; don't build on it.)

What each side may assume

  • A server may not assume the model will call its tools. It only offers.
  • A server may not infer anything from earlier requests on the same connection — not the version, not the capabilities, not the caller. Each request restates them.
  • A server may not read the conversation, and may not initiate requests. If it needs something back, it returns resultType: "input_required" and waits for the client to retry.
  • A host must not auto-approve destructive tools. Consent lives in the host, which is why servers stay simple.
