Chapter 5

Streamable HTTP

One POST-only endpoint. No sessions, no GET stream, no resumability — which means an MCP server is now just a stateless HTTP service, and you already know how to run one of those.

What this revision deleted. Mcp-Session-Id and its DELETE teardown, the standalone GET SSE stream, server-initiated JSON-RPC requests on a stream, and Last-Event-ID resumability. An older client using any of them gets 405, or is ignored.

The shape

Every message is its own POST. The server picks JSON or SSE per request.

Body Server answers
A request 200 with application/json, or text/event-stream if it wants to stream
A notification 202 Accepted, no body
An unimplemented method 404 — with a JSON-RPC -32601 body, so it's distinguishable from a wrong URL
GET or DELETE 405 — those were the session mechanics

Headers mirror the body

Selected body fields are duplicated into headers so load balancers, gateways and WAFs can route without parsing JSON. All of them are required. 

POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: roll_dice
Mcp-Param-Sides: 20

{ "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": { "name": "roll_dice", "arguments": { "count": 3, "sides": 20 },
              "_meta": { "io.modelcontextprotocol/protocolVersion": "2026-07-28", ... } } }
Header Mirrors Required for
MCP-Protocol-Version _meta protocol version every POST
Mcp-Method method every POST
Mcp-Name params.name or params.uri tools/call, resources/read, prompts/get
Mcp-Param-{Name} a tool argument marked x-mcp-header whenever that argument is present
Why the server must validate the duplication. If a gateway routes on the header and the server executes on the body, a mismatch is two components disagreeing about what the request is — a real privilege-escalation shape. So any mismatch, or a missing required header, is 400 with -32020 HeaderMismatch. Never reconcile; reject.

A client that omits a required Mcp-Param-* while sending the value in the body is non-conforming and must be rejected too. Values that don't fit in an ASCII header arrive Base64-wrapped, and the server decodes before comparing: 

Mcp-Name: =?base64?cm9sbF9kaWNl?=      // decodes to roll_dice

Integers compare numerically, so Mcp-Param-Sides: 20 matches a body value of 20.

Declaring a mirrored parameter

sides: {
  type: "integer",
  minimum: 2,
  maximum: 1000,
  "x-mcp-header": "Sides",   // becomes Mcp-Param-Sides
}

Only primitives (string, integer, boolean — not number), only properties reachable through a plain chain of properties keys, and never anything sensitive: header values are visible to every intermediary on the path.

Streaming

Two streams exist, and both are just a response body.

Per-request: progress

If the client puts a progressToken in _meta, the server may answer with SSE: notifications relating to this request, then the final response, then close. 

data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"p1","progress":1,"total":3,"message":"round 1 of 3"}}

data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"p1","progress":2,"total":3,"message":"round 2 of 3"}}

data: {"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","content":[{"type":"text","text":"Round 3 won with 20"}]}}

In our SDK the tool handler just calls context.progress(...); on a non-streaming transport, or when the client didn't ask, it's a no-op.

Long-lived: subscriptions/listen

The client opts into notification types; the response stream stays open and carries only those, each tagged with io.modelcontextprotocol/subscriptionId. 

data: {"jsonrpc":"2.0","method":"notifications/subscriptions/acknowledged","params":{"_meta":{"io.modelcontextprotocol/subscriptionId":"0589e605-..."}}}

data: {"jsonrpc":"2.0","method":"notifications/tools/list_changed","params":{"_meta":{"io.modelcontextprotocol/subscriptionId":"0589e605-..."}}}

Request-scoped notifications never appear here. Emit an SSE comment line (:\r\n) periodically or intermediaries will drop an idle stream.

Closing the stream is the cancellation signal. Each request owns its stream, so a disconnect is unambiguous — there is no notifications/cancelled on HTTP. Stop the work and send nothing more. And since streams aren't resumable, a broken one means the client re-issues the request with a new id; don't try to replay.

Security

  • Validate Origin. A browser cannot forge it, so an unexpected value means a page is talking to your server — respond 403. This is the DNS-rebinding defence.
  • Bind to 127.0.0.1 for local servers, not 0.0.0.0.
  • Authenticate. Credentials are per-request input, not connection state — which is also what lets tools/list legitimately vary by the caller's scopes.
  • Send X-Accel-Buffering: no on SSE or nginx will batch your events.
  • Ignore Mcp-Session-Id and Last-Event-ID if an old client sends them. Don't mint session ids.

Authorization

Optional in MCP, and the moment your endpoint is reachable from a network it stops being optional in practice. An MCP server never issues tokens — it is an OAuth 2.1 resource server: it validates what a client presents, and tells an unauthenticated one where to go and get one. 

// 401 — no credential at all
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp",
                         scope="dice:roll"

// 403 — authenticated, but the token lacks a scope this operation needs
WWW-Authenticate: Bearer error="insufficient_scope", scope="files:write",
                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp"

The resource_metadata pointer is the part clients actually need: it is how they discover which authorization server to use. Servers MUST implement that document (RFC 9728), naming at least one issuer: 

GET /.well-known/oauth-protected-resource/mcp

{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://auth.example.com"],
  "bearer_methods_supported": ["header"],
  "scopes_supported": ["dice:roll"]
}

The path is derived from the canonical resource URI: an endpoint at /mcp puts its metadata at /.well-known/oauth-protected-resource/mcp, and a client falls back to the root form if that 404s.

Audience binding is the rule that matters. Validate that each token was issued for this server. Accepting one minted for another service — or forwarding a token onwards — is the confused-deputy attack the spec explicitly forbids: "MCP servers MUST NOT accept or transit any other tokens."

Three smaller rules worth knowing:

  • 401 vs 403. Missing or invalid token is 401; a valid token without the scope is 403 with error="insufficient_scope".
  • Challenge with every scope the operation needs, at once. Returning them one at a time forces repeated authorization round-trips for a single call.
  • Dynamic Client Registration is deprecated in this revision, in favour of Client ID Metadata Documents. It remains only for authorization servers that do not support them.

In this SDK that is one option on the server:

new McpServer(info, {
  http: { auth: { resource, authorizationServers, verify } },
})

The verified caller then reaches handlers as context.identity, and context.hasScope() lets a single tool require more than the endpoint does. Because credentials are per-request input rather than connection state, every call re-authorizes — including a call against a handle you minted a request earlier.

What statelessness bought you

This is the payoff of everything in Chapter 2. Because no request depends on a previous one:

  • No session store, no Redis, no sticky sessions — round-robin across instances is correct.
  • An instance can be killed mid-flight; the client retries with a new id.
  • Responses are ordinary HTTP, so ordinary caching applies — that's what ttlMs and cacheScope are for.
  • The transport is the only thing that changes: in our SDK, McpServer never mentions HTTP at all — handle() is message-in, message-out, and the transport is the only thing that knows about requests. 
// src/server.ts — the MCP endpoint is one route on an ordinary Bun server
import { mcpServer } from "./mcp/server"

Bun.serve({
  hostname: "127.0.0.1",
  port: 3001,
  routes: {
    "/health": () => new Response("OK"),
    // Every method, not just POST: the transport answers GET and DELETE with 405.
    "/mcp": mcpServer.fetch,
    // RFC 9728 metadata, present only when authorization is configured.
    ...mcpServer.wellKnownRoutes(),
  },
})

That is the entire integration: one route on the same server that serves these pages. Try it with bun dev, then POST to http://127.0.0.1:3001/mcp with the headers above.
