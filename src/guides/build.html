Chapter 4

Build a server from scratch

No SDK, no dependencies, speaking 2026-07-28 over Streamable HTTP. A few dozen lines get you a working MCP endpoint; then we fold the protocol parts into a reusable SDK so adding a tool is four lines.

Why no SDK first? The official SDKs hide the _meta validation, the header mirroring and the error mapping — exactly the material you are trying to learn. Build it once by hand, then use the SDK forever after.

Step 1 — one POST endpoint

That is the whole transport surface. GET and DELETE were the session mechanics of older revisions, so answering 405 is how an old client learns they are gone. 

Bun.serve({
  hostname: "127.0.0.1",
  port: 3001,
  routes: {
    "/mcp": async (req) => {
      if (req.method !== "POST") return new Response("Method not allowed", { status: 405 })

      // A browser cannot forge Origin, so an unexpected one means a web page
      // is talking to us — the DNS-rebinding defence.
      const origin = req.headers.get("origin")
      if (origin !== null && !ALLOWED.includes(origin)) return json(403, ...)

      const msg = await req.json()
      return handle(msg)
    },
  },
})

Step 2 — validate _meta on every request

There is no handshake to remember, so this runs every time. Missing fields are -32602; a version you do not speak is -32022 carrying the list you do. 

const VERSION_KEY      = "io.modelcontextprotocol/protocolVersion"
const CAPABILITIES_KEY = "io.modelcontextprotocol/clientCapabilities"

function requireProtocolMeta(meta) {
  const version = meta?.[VERSION_KEY]
  if (typeof version !== "string" || meta?.[CAPABILITIES_KEY] === undefined) {
    throw new RpcError(-32602, `_meta must carry ${VERSION_KEY} and ${CAPABILITIES_KEY}`)
  }
  if (version !== PROTOCOL_VERSION) {
    throw new RpcError(-32022, "Unsupported protocol version", {
      supported: [PROTOCOL_VERSION],
      requested: version,
    })
  }
  return { version, capabilities: meta[CAPABILITIES_KEY] }
}

Step 3 — check the headers against the body

Streamable HTTP mirrors body fields into headers so gateways can route without parsing JSON. If the two disagree, one of them is lying — reject with -32020 rather than picking a side. 

if (headers.get("mcp-method") !== msg.method) return mismatch("Mcp-Method")
if (NAMED.has(msg.method) && decode(headers.get("mcp-name")) !== msg.params?.name) ...

Values that cannot ride in an ASCII header arrive Base64-wrapped as =?base64?…?=, so decode before comparing. Integers compare numerically.

Step 4 — dispatch

server/discover is mandatory. The initialize case is a courtesy: a legacy client cannot fall forward, so that message may be the only diagnostic its user ever sees. 

function dispatch(msg) {
  if (msg.method === "initialize") {
    throw new RpcError(-32601,
      `This server is stateless and has no initialize handshake. Supported versions: ${PROTOCOL_VERSION}`)
  }

  const meta = requireProtocolMeta(msg.params?._meta)

  switch (msg.method) {
    case "server/discover":
      return { supportedVersions: [PROTOCOL_VERSION], capabilities: { tools: {} },
               ttlMs: 3_600_000, cacheScope: "public" }
    case "tools/list":
      return { tools: TOOLS, ttlMs: 300_000, cacheScope: "public" }
    case "tools/call":
      return callTool(msg.params, meta)
    default:
      throw new RpcError(-32601, `Method not found: ${msg.method}`)
  }
}

Every result also needs resultType, and should identify the server — stamp both centrally: 

result: { resultType: "complete", ...body, _meta: { [SERVER_INFO_KEY]: INFO } }

Step 5 — the tool

Note the two failure styles: an unknown tool is a protocol error, but bad arguments the model could fix come back as a result with isError so it can read the message and retry. 

function rollDice(count, sides) {
  if (!Number.isInteger(count) || count < 1 || count > 100) {
    return { content: [{ type: "text", text: "count must be an integer between 1 and 100" }], isError: true }
  }

  const rolls = Array.from({ length: count }, () => 1 + Math.floor(Math.random() * sides))
  const total = rolls.reduce((sum, roll) => sum + roll, 0)
  return {
    content: [{ type: "text", text: `Rolled ${count}d${sides}: ${rolls.join(", ")} (total ${total})` }],
    structuredContent: { rolls, total },
  }
}

Step 6 — drive it with curl

curl -sS http://127.0.0.1:3001/mcp \
  -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -H 'mcp-protocol-version: 2026-07-28' \
  -H 'mcp-method: tools/list' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{
       "io.modelcontextprotocol/protocolVersion":"2026-07-28",
       "io.modelcontextprotocol/clientCapabilities":{}}}}'

Send a stale version and you should get -32022 with a supported list. Drop _meta and you should get -32602. Drop Mcp-Method and you should get -32020. That is the whole conformance surface, testable from a shell.

Step 7 — extract the SDK

Look back at what we wrote. Only two functions were about dice; everything else — _meta validation, version rejection, header checking, server/discover, resultType stamping, error mapping — is identical for every server that will ever exist. That is the SDK.

src/mcp/sdk/ holds all of it, one concern per file:

src/mcp/
  sdk/
    index.ts      public surface — what a server imports
    server.ts     McpServer: registries, dispatch, handle()
    context.ts    RequestContext: per-call state, answer() / elicit() / progress()
    protocol.ts   version, _meta keys, error codes, RpcError
    results.ts    text() / toolError()
    resources.ts  uri template matching, content builders
    prompts.ts    message builders
    types.ts      shared types
    http.ts       transport: Streamable HTTP
    headers.ts      - header mirroring and validation
    sse.ts          - the two SSE stream shapes
    auth.ts       OAuth 2.1 resource server
  server.ts       the dice server: tools, resources and prompts
  auth-config.ts  token verification for this deployment

A server then declares what it offers and nothing else:

import { McpServer, text, toolError } from "./sdk"

export const mcpServer = new McpServer(
  { name: "dice-server", version: "1.0.0" },
  { instructions: "Rolls dice. Call roll_dice with a count and a number of sides." },
)

mcpServer.tool(
  {
    name: "roll_dice",
    description: "Roll N dice with S sides each and return the individual rolls and their total.",
    inputSchema: { type: "object", properties: { /* ... */ }, additionalProperties: false },
    annotations: { readOnlyHint: true, openWorldHint: false },
  },
  (args) => rollDice(Number(args.count ?? 1), Number(args.sides ?? 6)),
)

and one route serves it:

Bun.serve({
  routes: {
    "/mcp": mcpServer.fetch,
    ...mcpServer.wellKnownRoutes(),
  },
})

What the SDK is hiding

You write The SDK does
new McpServer(info, options) Answers server/discover with supported versions, the capabilities you actually registered, instructions and cache hints; stamps serverInfo into every result
server.tool(definition, handler) Serves tools/list with ttlMs and cacheScope, and routes tools/call
server.resource(definition, read) Serves both list methods and routes resources/read — exact uris first, then {variable} templates
server.prompt(definition, handler) Serves prompts/list, checks required arguments, routes prompts/get
server.fetch Method and origin checks, authorization, content negotiation, header mirroring, version rejection, SSE when streaming is called for, and the JSON-RPC-to-HTTP status mapping
text() / toolError() Builds the content array, and keeps tool failures as results rather than protocol errors

The MRTR ergonomics

The awkward part of a stateless protocol is asking a question. The context object makes both halves of the round trip read like one function: 

(_args, context) => {
  const answer = context.answer<{ sides?: number }>("how_many_sides")
  if (answer) return rollDice(1, Number(answer.sides ?? 6))    // second call

  return context.elicit("how_many_sides", {                    // first call
    message: "How many sides should the die have?",
    schema: { type: "object", properties: { sides: { type: "integer" } }, required: ["sides"] },
  })
}

answer() reads params.inputResponses and returns undefined unless the user accepted. elicit() builds the input_required result — and first checks the client declared elicitation, throwing -32021 with requiredCapabilities if not, because a server must never send an input request the client cannot service.

Against the official SDK

Ours is around 900 lines across twelve files and covers all three primitives, both SSE stream shapes and OAuth resource-server support. @modelcontextprotocol/sdk adds stdio, subscriptions in depth, pagination, schema validation and far more — but the shape is the same, and you now know exactly what it is doing for you. Check which protocol revision your SDK version targets before assuming it is modern; the era matters more than the package version.
