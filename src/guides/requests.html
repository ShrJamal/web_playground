Chapter 2

Stateless requests

As of revision 2026-07-28 there is no handshake and no session. Every request is self-contained: it carries its own protocol version and capabilities, and any server instance can answer it.

If you learned MCP before this. initialize, notifications/initialized, and the Mcp-Session-Id header are gone. Revisions up to 2025-11-25 are now called legacy; 2026-07-28 and later are modern. See backward compatibility below.

Three message shapes

// Request — has an id, expects a response
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": { "_meta": { ... } } }

// Result — same id, and a required resultType
{ "jsonrpc": "2.0", "id": 1, "result": { "resultType": "complete", "tools": [] } }

// Error — same id
{ "jsonrpc": "2.0", "id": 1, "error": { "code": -32601, "message": "Method not found" } }

// Notification — no id, no response, ever
{ "jsonrpc": "2.0", "method": "notifications/tools/list_changed" }
resultType is required now. "complete" for an ordinary result, "input_required" when the server needs something back before it can finish. A result from an older server that omits the field is treated as "complete".

What every request carries

The metadata that used to be exchanged once, at initialize, now rides along in params._meta on every single request. 

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "roll_dice",
    "arguments": { "count": 3, "sides": 20 },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion":    "2026-07-28",   // REQUIRED
      "io.modelcontextprotocol/clientCapabilities": { "elicitation": {} },  // REQUIRED
      "io.modelcontextprotocol/clientInfo":         { "name": "ExampleClient", "version": "1.0.0" }
    }
  }
}

The server answers in kind, identifying itself in the result's _meta: 

"result": {
  "resultType": "complete",
  "content": [{ "type": "text", "text": "Rolled 3d20: 10, 7, 13 (total 30)" }],
  "_meta": { "io.modelcontextprotocol/serverInfo": { "name": "dice-server", "version": "1.0.0" } }
}

The metadata did not disappear; it moved from a one-time handshake onto every request.

Version negotiation without a handshake

The client states its version on the request. A server that doesn't support it rejects that request with -32022 and lists what it does support; the client picks one and retries. 

{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": { "supported": ["2026-07-28", "2025-11-25"], "requested": "1900-01-01" }
  }
}

server/discover

Servers MUST implement it; clients MAY skip it. It's one request that returns versions, capabilities, identity and usage instructions — handy for showing a server in a UI, and used as the era probe on stdio. 

// -> server/discover  (params: just _meta)
// <- result
{
  "resultType": "complete",
  "supportedVersions": ["2026-07-28"],
  "capabilities": { "tools": {}, "resources": {} },
  "instructions": "This server provides weather and resource utilities.",
  "ttlMs": 3600000,
  "cacheScope": "public",
  "_meta": { "io.modelcontextprotocol/serverInfo": { "name": "ExampleServer", "version": "1.0.0" } }
}

Where state went

The protocol has no session, so anything spanning calls must be an explicit, server-minted handle passed as an ordinary tool argument: 

// -> tools/call create_basket {}
// <- structuredContent { "basket_id": "bsk_a1b2c3" }
// -> tools/call add_item { "basket_id": "bsk_a1b2c3", "sku": "..." }

The model carries the handle forward. Treat a handle as a name, not a capability: re-check authorization on every call, keep it opaque, give it a bounded lifetime, and say so in the tool description.

Also gone with sessions: list results must not vary per-connection, an open stdio process is not a conversation, and SSE stream resumability (Last-Event-ID) is removed — a broken stream means re-issuing the request with a new id.

Caching replaces polling

tools/list, prompts/list, resources/list, resources/read and resources/templates/list must return ttlMs (freshness hint) and cacheScope ("public" or "private"). Return tools in a deterministic order so client caches and prompt caches actually hit.

Error codes

Code Name When
-32700 Parse error Body wasn't valid JSON
-32600 Invalid request Not a valid JSON-RPC object
-32601 Method not found Unknown method name
-32602 Invalid params Missing _meta, unknown tool, resource not found
-32603 Internal error Your handler threw
-32020 HeaderMismatch HTTP header disagrees with the body
-32021 MissingRequiredClientCapability Request needs a capability the client didn't declare
-32022 UnsupportedProtocolVersion Version in _meta not supported

-32020–-32099 is now reserved for the spec: don't invent codes there. -32002 (resource not found) is retired in favour of -32602, though clients should still accept it from older servers.

Tool failures are not protocol errors. A tool that fails (API down, bad date, value out of range) returns a normal result with isError: true and the message in content, so the model can read it and self-correct. Reserve JSON-RPC errors for unknown tools, malformed requests and server faults. This has not changed, and it is still the most common beginner bug.

Backward compatibility

A dual-era server can serve both: a request with modern _meta is served statelessly, an initialize request selects legacy semantics. A dual-era client detects the era per server and caches the answer:

  • stdio: probe with server/discover. A DiscoverResult or a recognised modern error means modern; any other error, or a timeout, means legacy — fall back to initialize. Never key the fallback to one error code.
  • Streamable HTTP: send a modern request and inspect the body of a 400 before falling back.

Dual-era in practice

This is not hypothetical. Claude Code 2.1.263 still opens with:

{"method":"initialize","params":{"protocolVersion":"2025-11-25",
 "capabilities":{"roots":{"listChanged":true},"elicitation":{}},
 "clientInfo":{"name":"claude-code","version":"2.1.263"}},"id":0}

A modern-only server answers that with an error and the connection fails — the "Legacy client → Modern server" row above. Supporting both eras costs very differently by transport:

Transport What dual-era costs
stdio Answer initialize, remember the negotiated version and capabilities for the process, and reconstruct from them the _meta a modern request would have carried. Around 70 lines.
Streamable HTTP All of that plus the machinery this revision deleted: Mcp-Session-Id and a session store, sticky routing, a standalone GET SSE stream, and Last-Event-ID replay.
Which is why the SDK in this repo is modern-only. Bridging the eras over HTTP means reimplementing the stateful transport you adopted HTTP to escape. The trade is real: today's Claude Code cannot connect to it. Check what your target clients speak before choosing.

A modern-only server should name its supported versions in whatever error it returns to initialize — a legacy client has no way to fall forward, and that message may be the only diagnostic its user ever sees.
